01为什么必须建评测体系

主规划（docs/EduMeet建设规划.html v1.5）中，四大核心能力都存在「效果/资金不可度量」的风险敞口，单点验收阈值无法覆盖持续变更带来的质量漂移：

🎯

政策内容零容忍出错

面向家长的教育政策问答与生成内容，一旦幻觉出错会直接误导升学决策。核查 Agent 只能拦截已知风险，需要金标数据集持续度量实体级事实准确率。

🔄

模型不固定、分批接入

模型按 P0/P1/P2 分批接入且随行情热切换（Spec 07），每次切换都是一次「质量未知」的变更，必须靠统一数据集的对比评测支撑选型与降级决策。

🧩

多智能体链路复杂

文章生成是 5 Agent 流水线（规划→写作→配图→核查→审核，Spec 04），任何 Prompt/节点变更都可能引起级联质量退化，需要逐环节记分卡定位退化点。

💰

计费是资金级零容错

积分扣费链路（Spec 11：两阶段扣费、双余额 FIFO、沙箱控制）直接关联真金白银——多扣引发客诉退款与信任损失，少扣是直接资损，必须以「误差=0」的资金级标准评测。

定位：评测体系是 EduMeet 的「质量基础设施」，与业务功能同步建设——冒烟评测集随 M1 流水线一起交付，评测平台随 M2 完整落地，计费资金级专项随 M3（会员计费上线同期）生效，模型对比评测每季度驱动一次选型复审。独立目录 评测/ 管理，不影响主工程代码。

07评测方法：四层评测法

📏

L1 规则校验

零成本：结构完整性、格式合法性、引用可访问、时效标注存在性、JSON Schema 校验、计费金额确定性断言（金标由公式推导）。

📊

L2 统计指标

标准 IR/NLP 指标：NDCG、MRR、Recall、RAGAS 四件套；property-based 随机组合 fuzz（Hypothesis，用于计费公式百万组合扫描），脚本确定性计算。

⚖️

L3 LLM-as-Judge

用固定强模型（GLM-5 / GPT-4o，与被评模型隔离）按 Rubric 评分：事实准确、要点覆盖、图文相关、教育适配性。计费/安全等确定性指标禁用 LLM 评分。

👤

L4 人工评审

金标校准、争议仲裁、上线前抽检 20%、季度标注漂移审计。

7.1 LLM-as-Judge 可信度保障

  • 隔离原则：Judge 模型不得与被评模型同源（豆包/DeepSeek/Qwen 被评时用 GLM-5 或 GPT-4o 评审，反之亦然）。
  • 校准机制：Judge 上岗前先对 50 条人工标注样本盲测，与人评一致率 ≥ 85% 才可启用；每季度复测。
  • Rubric 版本化：评分标准存 Git，随评测集版本联动，变更需评审。
  • 防偏置：评分打乱样本顺序、隐藏模型来源、对长文分段评分。
  • 适用边界：LLM-Judge 仅用于主观/语义类指标；凡可用确定性断言的指标（计费金额、拦截结果、结构完整性）一律走 L1/L2，杜绝 Judge 引入的随机误差进入零容忍级门禁。

08计费正确性评测：资金级零容错

积分即真金白银（1 元 = 10 积分，Spec 11）。计费评测与内容质量评测有本质区别：它不依赖 LLM 判断，全部为确定性断言；它不是「尽量高」，而是「必须为零误差」。本专项随 M3 会员计费上线同期建成，门禁与安全指标同级——一票否决。

8.1 六类资金级评测

#评测类型方法断言（全部量化）
1公式 Oracle 测试以 Spec 11 公式为 oracle 做 property-based 测试（Hypothesis 随机生成输入/输出 token 组合 × 全档位模型价目 × 1.05 利润系数），并与固定金标用例双向覆盖百万级随机组合扫描：扣费金额与公式推导金标误差 = 0；ceil 取整边界无一例外
2扣费事务与幂等同 ref_id 重放 N 次；中途失败重试；退款链路精确回冲；两阶段扣费（预检→按实际 usage 结算）各阶段注入异常重放 N 次仅扣 1 次（重复 = 0）；失败全额退还（退款误差 = 0）；balance_after 链条连续无跳变
3双余额 FIFO赠送积分（按月过期）先扣、充值积分（永久）后扣的序列断言；月末过期边界、跨月叠加、加油包混扣扣减顺序与 Spec 11 规则完全一致；过期清零不误删充值余额；余额永不为负
4并发竞态同账户 100 并发扣费/充值/退款混合压测（影子账户 + 事务隔离级别验证：行锁/乐观锁）恰好扣 N 次（超扣/漏扣 = 0）；无负余额；无死锁挂起
5沙箱逃逸矩阵免费用户 × 全部付费模型直连、伪造 model_ref、篡改响应 usage、SSE 流中断、免费日额度跨日重置边界、会员过期瞬间调用逃逸 = 0：100% 拦截（40302/40304）或自动降级免费模型；无一次未授权模型消耗
6对账三道闸①请求内自检：扣费流水 balance_after 链连续性校验；②T+1 日切对账：日流水聚合 vs 余额快照核对；③月度反核：厂商账单实际 usage × 单价 vs 平台扣费流水三道闸差异均 = 0；差异 > 0 触发 P0 资损告警并冻结对账差异账户

·
DB 主从延迟

8.3 门禁与规则联动

  • 发布门禁：计费四项量化指标（误差/逃逸/幂等/对账）任一不为 0，禁止发布，与安全一票否决同级。
  • 规则-用例版本绑定：Spec 11 任何规则变更（单价/汇率/利润系数/等级权益）的 PR 必须同步更新 DS6 金标与断言，评测集版本号与规则文档版本号绑定，防止规则与用例漂移。
  • 线上资损监控（D8 联动）：生产环境资损告警规则常驻——扣费流水与 LLM 网关 usage 小时级抽样比对、对账闸门定时任务、异常大额扣费（单笔 > P99.9）实时告警。
  • 评测环境隔离：并发/混沌用例跑在独立影子账户与独立 DB 实例，禁止污染生产数据。
